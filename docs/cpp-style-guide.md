# C++ コーディング規約

この文書は、Kagutsuchi の C++ コードで共通して使う規約を定めます。迷った場合は、既存コードとの一貫性を優先し、読みやすさと安全性を保てる選択をしてください。

## 対象と基本方針

- C++20 を標準とし、コンパイラ固有の拡張に依存しないコードを基本とします。
- 規約はコードレビューで一貫性を保つためのものです。機械的な整形が可能な項目は将来 formatter で自動化します。
- C++ の書式整形には `clang-format` を使い、リポジトリルートの `.clang-format` 設定に従います。識別子の命名など、formatter で扱えない規約も引き続き本書に従います。
- 既存コードを変更する際は、変更範囲に関係のない大規模な整形を避けます。

## ファイルと命名

- ファイル名は小文字の `snake_case` とし、ヘッダーは `.hpp`、実装は `.cpp` を使います。
- 公開ヘッダーは `lib/<module>/include/kagutsuchi/<module>/` に置き、実装詳細は `src/` に置きます。
- 名前空間は `kagutsuchi::<module>` を基本とします。
- 型名（クラス、構造体、列挙型、型エイリアス）は `PascalCase` を使います。
- 関数名・メソッド名（公開・非公開、static を含む）は `lowerCamelCase` を使います。
- 変数名（ローカル変数、引数、メンバー変数）は `lowerCamelCase` を使います。ただし private メンバー変数には末尾 `_` を付けます。
- public メンバー変数や struct のデータメンバーには末尾 `_` を付けません。
- 定数と列挙子は `PascalCase` を使い、定数に `k` 接頭辞は付けません。
- マクロは既存 API や外部仕様との接続に必要な場合に限り、`KAGUTSUCHI_` で始まる大文字の `SNAKE_CASE` にします。
- 名前に型や所有権を重複して埋め込まず、役割が分かる具体的な名前を選びます。

```cpp
namespace kagutsuchi::physics {

inline constexpr double DefaultTimeStep = 1.0 / 60.0;

class ParticleSystem {
public:
    void advance(double timeStep);
};

}  // namespace kagutsuchi::physics
```

## 書式

- インデントはスペース 4 つとし、タブは使いません。
- 波括弧は関数・型・制御文の開始位置で改行します（Allman 形式）。
- 1 行は原則 100 文字以内を目安とし、読みやすい位置で折り返します。
- ポインター・参照の `*` / `&` は型側に付けます（`Type* value`、`const Type& value`）。
- `if`、`for`、`while` などの本体が 1 行でも波括弧を省略しません。
- 名前空間の閉じ括弧には、必要に応じて名前空間名のコメントを付けます。

## ヘッダーと依存関係

- ヘッダーには必要な宣言だけを置き、可能なら前方宣言でヘッダー間の依存を減らします。
- `#include` は対応する標準ヘッダー、外部ライブラリ、プロジェクト内ヘッダーの順にグループ化します。各グループ内はアルファベット順を基本とします。
- 実装ファイルでは、対応する公開ヘッダーを最初に include し、ヘッダーが自己完結していることを確認しやすくします。
- ヘッダーガードは `#pragma once` を使います。
- `using namespace` はヘッダーおよび名前空間スコープで使いません。必要なら関数内で限定的に使います。
- 公開 API は最小限に保ち、実装用の詳細を公開ヘッダーへ漏らしません。

## 型、安全性、所有権

- 所有権は RAII で表現し、リソース管理には標準ライブラリの型を優先します。
- 動的所有が必要な場合は `std::unique_ptr` を基本とし、共有所有が必要な理由がある場合だけ `std::shared_ptr` を使います。
- 所有権を持たない参照には参照または明示的なポインターを使い、null が許されるポインターにはその条件を明確にします。
- 変更しない値には `const` を付けます。ローカル変数は必要になる地点で初期化し、未初期化状態を作りません。
- 固定幅が必要な整数には `<cstdint>` の `std::int*_t` / `std::uint*_t` を使います。サイズや要素数には適切な符号なし型（通常 `std::size_t`）を使います。
- `auto` は右辺から型が明確な場合や、型名の重複を避けて可読性が上がる場合に使います。
- キャストは目的に合う名前付きキャストを使い、C 形式キャストは使いません。
- `enum class` を使い、スコープのない列挙型を避けます。

## 関数とエラー処理

- 関数は一つの責務に絞り、引数が多くなった場合は関連する値を型にまとめることを検討します。
- 入力値の変更が不要なら値渡し・参照渡しを選びます。小さくコピー可能な型は値渡し、それ以外は通常 `const T&` を使います。
- 仮想関数をオーバーライドするときは `override` を付けます。基底クラスとして使う型のデストラクターは適切に `virtual` にします。
- エラーはプロジェクト内で採用されている戻り値型または例外方針に従います。失敗を握りつぶさず、呼び出し側が扱える形で伝えます。
- `assert` は開発時の不変条件確認に使い、ユーザー入力や実行時エラーの処理の代わりにはしません。

## コメントとドキュメント

- ログメッセージは英語で記述します。
- コードコメントは原則として日本語で記述します。コメントはコードの動作の言い換えではなく、理由・前提・制約を説明します。
- 公開 API には Doxygen 形式のコメントを書き、用途・引数の制約・戻り値・失敗条件など、利用者が必要とする情報を日本語で記述します。
- TODO には可能なら担当や追跡先を付け、放置された未完了事項にならないようにします。

## Vulkan 固有のコード

- Vulkan ハンドルや割り当て済みリソースの所有者と破棄タイミングを明確にします。
- Vulkan の同期、キュー所有権、レイアウト遷移の前提は、非自明な箇所に短く記録します。
- Vulkan の列挙値やフラグを扱う際は、暗黙の整数変換に頼らず、意図が分かる型と変換を使います。

## ビルド・レビュー

- 警告は原則として修正し、警告抑制を追加する場合は対象を絞り理由を記録します。
- CMake のターゲット単位で依存とコンパイル設定を管理し、グローバル設定を不用意に追加しません。
- 変更後はプロジェクトの標準プリセットでビルドし、テストがある場合は関連テストを実行します。
